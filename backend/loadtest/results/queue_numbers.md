## 판정·관찰·추천

- **잠정 기준(사용자 확정 대상): 구매 p95 ≤ 1s, p99 ≤ 2s; 모든 API 5xx=0, 비409 오류율 <0.1%.**
- 등록 → 서버 nextPollAfterMs 준수 status → 실제 Worker 입장 → enter → 좌석 요약/구역 3회 → 생각 시간 → 구매 1회.
- 총 2,000명, 오픈 직후 1,000명/10초 500명/30초 500명 도착. ACTIVE 생각 시간 75~90초, TTL 5분·Worker fixedDelay 5초 유지.
- 고유 빈 좌석이므로 전원 201·완료/미발송·HTTP↔DB 검사도 유효성 조건. capacity(ADMITTED+ACTIVE) 표본이 max의 80% 미만이면 해당 max 검증 불충분으로 추천 제외.

## 결정 (2026-10-08)

- 사용자가 max-concurrent=1000, admit-per-cycle=100을 확정했다(설계값이며 application.yaml도 동일). 위 자동 추천(2000/200)은 채택하지 않는다.
- 7조합이 모두 잠정 기준(구매 p95 ≤ 1s, p99 ≤ 2s, 5xx 0, 409 외 오류율 < 0.1%)을 통과해 기준으로는 조합을 가를 수 없다. 자동 추천은 "통과하는 최대값"일 뿐이다.
- admit 200은 입장 p95가 0.8~1.2s, 좌석 조회 p95가 0.1~0.35s로 튀었다. 1000/100은 구매 45ms, 입장 19ms, 좌석 30ms이고 2,000명 처리에 약 2.5분이 걸렸다.
- 2000/100은 약 40% 빠르지만 점유가 상한 2,000까지 차지 않아(최대 1,740) 검증이 불충분하다.
- 로컬 8코어에서 k6·앱·DB를 함께 돌린 잠정값이므로 운영 재측정이 필요하다. 판정 기준은 잠정 기준 그대로 둔다.
- 관찰(미조치): 등록 API p95가 조합과 무관하게 1.3~2.0s다. 오픈 직후 DB 확인 때문에 Hikari 대기가 150~180까지 쌓인다. 개선 후보로만 기록한다.
